## Что уже сделано как задел

Решение «локально, но схема как под Postgres» было принято именно ради этого перехода. К сегодняшнему дню готово:

| Задел | Зачем понадобится |
|-------|-------------------|
| Схема описана таблицами, с типами и ограничениями | DDL уже написан, переносится почти без правок |

| Все вызовы асинхронные | Сеть не сломает ни одного обращения |
| Механизм миграций | Схема на сервере и на устройстве будут расходиться, это надо переживать |

Без этого задела переход означал бы переписывание всего. С ним — добавление слоя.

## Поправка к раннему решению

Раньше было записано: «`remoteAdapter` — тот же интерфейс поверх Postgres». **Это неверно, и вот почему.**

Замена адаптера означала бы, что каждое касание кружка идёт в сеть. В зале, в метро, в самолёте приложение перестанет работать вовсе, а тап по кружку начнёт зависать на секунды. Ради этого не стоило затевать местное хранилище.

**Правильно так:** локальное хранилище остаётся единственным, с чем работают модули. Postgres добавляется **сбоку**, отдельным слоем синхронизации.

```
модули → store → localAdapter → браузер устройства
                      ↕
                 синхронизация ⇄ Postgres
```

Приложение не замечает ни сети, ни её отсутствия. Синхронизация идёт фоном и переживает разрывы.

## Где будет жить база: свой сервер

**Решено.** База и всё вокруг неё — на собственном сервере. Данные не уезжают к стороннему поставщику, доступ к SQL прямой.

### Из чего это состоит

| Часть | Зачем | Замечание |
|-------|-------|-----------|
| Арендованный сервер | Место, где всё живёт | Самого дешёвого тарифа хватает с запасом |
| Postgres | Собственно база | Слушает только локально, наружу не смотрит |
| Обмен по сети | Браузеру нельзя ходить в базу напрямую | Две ручки, см. ниже |
| Обратный прокси с HTTPS | Без шифрования браузер запрос не выпустит | Caddy получает сертификат сам |
| Домен | Сертификат выдают на имя, не на адрес | Годится и дешёвый, и бесплатный поддомен |
| Резервные копии | Диск сервера — такая же смертная вещь | Слепок по расписанию, увозится с сервера |
| Обновления безопасности | Сервер смотрит в интернет круглосуточно | Автоматические обновления, вход только по ключу |

### Обмен: две ручки вместо готового решения

Соблазн поставить готовую надстройку, которая сама превращает таблицы в сетевой доступ, велик. Но она тянет за собой роли базы и построчные права доступа — механизм мощный и ровно поэтому опасный: ошибка в одном правиле открывает всё.

Для одного пользователя и обмена по времени изменения нужно ровно две ручки:

```
GET  /changes?since=<отметка>   отдать всё, что изменилось после
POST /changes                   принять пачку изменений
```

Это полторы сотни строк, которые целиком помещаются в голове и проверяются за вечер. Схему они не знают: принимают и отдают записи как есть, а форму проверяет та же схема, что и на устройстве.

**Доступ:** один долгоживущий пропуск, выданный при входе. Проверяется на каждый запрос. Разграничивать доступ между пользователями не требуется — пользователь один.

**Разрешённые источники:** только адрес приложения. Иначе любой сайт сможет дёргать ручки из браузера.

### Чего это стоит

Работы примерно на треть больше, чем с готовым поставщиком: добавляются настройка сервера, сертификат, резервные копии и обновления. Взамен — данные остаются своими, прямой доступ к SQL и отсутствие чужих правил игры.

Обслуживание не разовое. Сервер требует внимания раз в пару месяцев: обновления, проверка того, что резервные копии действительно снимаются и действительно восстанавливаются.

## Что добавится в схему

Три изменения, каждое через миграцию.

1. **Таблица `sync_state`.** Хранит отметку последней успешной отправки и приёма по каждой таблице. Без неё придётся каждый раз тянуть всё целиком.
2. **Индекс по `updated_at`.** Выборка «что изменилось с такого-то момента» — основной запрос синхронизации.

Поля `user_id` не будет: пользователь один, разграничивать нечего. Появится второй — добавится миграцией.

---

## Как работает синхронизация

**Отправка.** Берутся записи, у которых `updated_at` новее отметки последней отправки, и уходят пачкой. Сервер отвечает подтверждением, отметка сдвигается. Не ушло — остаётся до следующего раза.

**Приём.** Запрашиваются записи, изменённые на сервере позже отметки последнего приёма. Каждая сравнивается с местной по `updated_at`, побеждает более поздняя.

**Удаление** едет как обычное изменение: у записи проставлен `deleted_at`. Никакой особой обработки не требуется — ровно ради этого удаление и сделано мягким.

**Конфликт** разрешается по времени изменения. Для трекера этого достаточно: две правки одной записи с двух устройств в один и тот же момент — событие, которого практически не бывает.

**Когда запускается:** при открытии приложения, при возвращении сети и раз в несколько минут, пока приложение открыто. В фоне iOS ничего не выполняет, и рассчитывать на это нельзя.

**Что видит пользователь:** отметка в меню — когда прошла последняя синхронизация и сколько записей ждёт отправки. Не крутящееся колесо поверх экрана: синхронизация не должна мешать записывать воду.

| 7 | Отметка состояния и настройки в меню | **Готово** |

**Сервер развёрнут 25 августа 2026.** Ubuntu 24.04, одно ядро, гигабайт памяти. Обмен работает в обе стороны, перезагрузка пережита, три службы поднимаются сами. Инструкция исправлена по отчёту о развёртывании — расхождения были в окружении, а не в существе.

Код проверен на поддельном сервере целиком: отправка, отсутствие повторной отправки, приём чужой записи, отклонение устаревшей. Не проверено то, что нельзя проверить без настоящего сервера: сертификат, разрешённые источники, поведение при обрыве посреди пачки.

Шаги с первого по шестой сопоставимы по объёму со всем, что сделано до сих пор. Половина работы — не в коде, а в проверке того, как обмен ведёт себя при обрывах.

## Риски

1. **Сервер требует внимания.** Он смотрит в интернет круглосуточно. Забытые обновления превращают его в чужую машину. Вход только по ключу, пароли отключены, обновления безопасности автоматические.
2. **Резервная копия, которую не пробовали восстановить, — не резервная копия.** Проверка восстановления должна быть частью шага, а не намерением на будущее.
3. **Вход становится обязательным.** Сегодня приложение открывается и работает. После перехода понадобится пропуск, который можно потерять.
4. **Обслуживание не разовое.** Раз в пару месяцев: обновления, срок сертификата, проверка копий. Это не заканчивается никогда.
5. **Соблазн выкинуть местное хранилище.** Делать этого нельзя ни при каких обстоятельствах. Оно и есть приложение, а сервер — только копия.

---

## Решено

- **Зачем:** надёжность хранения и синхронизация между устройствами. Значит обмен двусторонний, а не отправка копий в одну сторону.
- **Где:** свой сервер.
- **Когда:** после того, как вода выйдет в прод.

## К чему вернуться на шаге 1

1. Есть ли уже арендованный сервер и домен или заводим с нуля.
2. На чём писать две ручки обмена — от этого зависит только удобство правок, на работу не влияет.
3. Как хранится пропуск на устройстве и что делать, если он потерян.
