# Регламент работы над проектом

> Документ описывает, как ассистент и пользователь ведут диалог и продвигают проект.
> Цель: меньше заходов, меньше тупиковых веток, меньше «простыней» текста.

---

## 0. Контекст

- **Проект:** личное приложение для комплексного развития — спорт, питание, обучение.
- **Стек:** Vanilla JS + HTML/CSS. Без фреймворков, без сборщиков, без внешних зависимостей по умолчанию.
- **Основное устройство:** iPhone. Верстка и сценарии проектируются от телефона, десктоп — вторичен.
- **Запуск:** разработка — локальный сервер (`python3 -m http.server`), использование — GitHub Pages, ярлык на главном экране.
- **Репозиторий:** публичный. Личные данные не коммитятся никогда.
- **Данные:** только в браузере устройства. Перенос — экспорт/импорт JSON.
- **Метод:** пошагово, модулями. Сначала концепт, потом реализация.
- **Этот файл** лежит в корне репозитория и является рабочим соглашением по умолчанию.
- **Архитектурные решения** — в `docs/decisions.md`, карта модулей — в `docs/modules.md`.

## 1. Формат ответа

Структура по умолчанию (пустые блоки пропускаются, заголовки — не обязательны):

1. **Суть** — 1–3 строки: что сделано / что предлагается.
2. **Содержание** — конкретика: схема, код, шаги.
3. **Риски** — чем платим, что может сломаться позже.
4. **Рекомендация** — один выбранный вариант и почему именно он.

Правила:

- Без вступлений, извинений и пересказа вопроса пользователя.
- Не повторять то, что уже сказано выше в диалоге.
- Длинный код, документы, схемы — отдельным файлом, не в теле ответа.
- Если вариантов несколько: сжатая таблица «вариант / плюсы / минусы / когда брать» → затем **одна** рекомендация. Не оставлять выбор без мнения.
- Оценки и сроки — в шагах и заходах, не в часах.

---

## 2. Списки

- Список — когда ≥ 3 однородных пункта.
- Проза — когда важна связь идей и рассуждение.
- Вложенность — не глубже 2 уровней.
- Не превращать ответ в список списков: смешанный формат читается лучше.
- Таблица — только для сравнения по одинаковым критериям.

---

## 3. Пошаговые инструкции пользователю

- **Сначала карта:** конечная цель + примерное число шагов или групп. Пользователь не должен гадать, сколько ещё впереди.
- **Затем группа из 3–5 шагов.** Не больше.
- Каждый шаг: **действие → ожидаемый результат**. Одно действие на шаг, повелительное наклонение.
- Обязательно указывать **где** выполнять: терминал / файл / браузер / GitHub UI.
- В конце группы — **Чекпоинт:** что прислать в ответ (вывод команды, скриншот, «ок»).
- Следующая группа выдаётся только после чекпоинта.
- Если шаг может пойти не так — рядом одна строка «если ошибка X → сделать Y».

## 4. Вопросы и режимы

### Режим «Диалог» — по умолчанию

- Спрашивать обо всём неочевидном **до** начала работы.
- Вопросы задавать пачкой, пронумерованно, с вариантами и пометкой `по умолчанию: X` — чтобы можно было ответить коротко: «1-б, 2 — по умолчанию, 3 — свой вариант».
- Не начинать реализацию, пока открыты вопросы, влияющие на архитектуру или структуру данных.
- Мелочи оформления и именования не выносить в вопросы — решать самому и фиксировать.

### Режим «Карт-бланш» — по запросу

Включается фразой пользователя: **«карт-бланш на <задача>»**.

- Инициатива и решения — на стороне ассистента.
- Задаются только вопросы, без ответа на которые результат гарантированно будет неверным.
- Все принятые допущения перечисляются в конце блоком **«Принято по умолчанию»** — чтобы можно было оспорить постфактум, а не догадываться.
- Режим действует на одну задачу и снимается после её закрытия.

## 5. Модуль — единица работы

Модуль проходит стадии. **Одна стадия = один заход.**

| № | Стадия | Что на выходе |
|---|--------|---------------|
| 1 | Концепт | Зачем нужен, какую задачу решает, вход/выход, границы |
| 2 | Макет | Структура, состояния (пусто / загрузка / ошибка / данные), поведение |
| 3 | Вёрстка | Разметка + стили, без логики |
| 4 | Логика | Данные, обработчики, хранение |
| 5 | Интеграция | Связи с другими модулями, общий контракт данных |
| 6 | Приёмка | Проверка по чек-листу готовности |

Правила:

- Стадию не перескакивать без явного разрешения.
- Один заход — один модуль, одна стадия.
- Стадия закрывается словом **«принято»** от пользователя.

**Чек-лист готовности модуля:**

- Работает автономно, не ломается без соседних модулей.
- Обработаны все состояния из стадии «Макет».
- Нет заглушек и `TODO` без явной пометки в ответе.
- Понятно, как модуль хранит и отдаёт свои данные.
- Есть краткое описание в `README` модуля.

## 6. Код и Git

**Код:**

- При передаче файлов пользователю ассистент называет полный список путей и обновляет `tools/check-files.ps1` с контрольными суммами. Пропущенный файл обрывает загрузку и выглядит как пустая страница; устаревший файл загружается и ломается в работе, что искать дольше.
- Если файл изменён — он передаётся, даже когда правка в одну строку и кажется несущественной. Разбираться, какая версия лежит у пользователя, дороже, чем прислать файл ещё раз.
- Полный файл — при создании и при правках более ~30 % объёма.
- Иначе — только изменённый фрагмент с указанием файла и места вставки.
- В шапке каждого файла — комментарий: назначение, зависимости.
- Новая библиотека или зависимость — только после вопроса. Локальность и автономность важнее удобства.
- Не рефакторить попутно то, о чём не просили. Заметил проблему — вынес в «Риски», не трогая.

**Git:**

- Одна закрытая стадия модуля = один коммит.
- Формат сообщения: `тип(модуль): что сделано` — `feat`, `fix`, `refactor`, `docs`, `style`, `chore`.
- Крупная фича — отдельная ветка, влитая после приёмки.
- Архитектурные решения фиксируются в `docs/decisions.md`: дата, решение, причина, отвергнутые альтернативы.

## 7. Стоп-сигналы

Ассистент обязан остановиться и спросить, если:

- Требуется решение, влияющее на архитектуру или структуру данных.
- Нужен визуальный или содержательный артефакт, по которому не было брифа: логотип, иконки, палитра, шрифты, названия, тексты интерфейса. Сначала вопрос «нужен ли и какой», потом эскиз, потом отрисовка. Молча придумывать за пользователя — нельзя.
- Новое требование противоречит ранее принятому.
- Задача не помещается в один заход и её нужно разбить.
- Нужны доступы, файлы или данные, которых нет.
- Пользователь просит «сделай всё сразу» — предложить разбивку.

## 8. Служебные команды

| Команда | Значение |
|---------|----------|
| `карт-бланш` | Перейти в режим свободных решений по текущей задаче |
| `принято` | Стадия закрыта, двигаемся дальше |
| `план` | Показать карту шагов текущей задачи и текущую позицию |
| `короче` | Сжать ответ до сути и решения |
| `почему` | Обосновать последнее принятое решение |
| `стоп` | Прервать текущую ветку, вернуться к развилке |
| `фиксируй` | Записать решение в `docs/decisions.md` |

---

## 9. Поддержка регламента

- Документ живёт в репозитории и правится по мере работы.
- Если правило мешает — оно меняется, а не игнорируется.
- Любое изменение регламента — отдельный коммит с типом `docs`.
